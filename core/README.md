# Tasktap core

The core is one Rust service that owns everything that is not pixels. This workspace is two crates: the protocol, and the core itself, which grows one module per package of the rebuild.

`proto/` (`tasktap-proto`) holds the wire types that exist so far: the ten frame kinds and their binary codec, the frozen bootstrap contract, the table of Phase 1 calls, and the records. It commits `proto/protocol.ts`, generated from those types, and `proto/samples/`, one sample per frame kind for checking other encoders.

The root crate (`tasktap-core`) has the store and the state machine so far: `src/store.rs` keeps every record in one SQLite file that only the core writes. Each committed transaction takes the next revision and returns the change subscribed clients are sent; the live rule moves old finished thoughts to history; the recovery pass at start closes what an earlier run left open and never starts anything. `tests/store.rs` proves it on temporary folders.

`src/state.rs` is the state machine of design §5, the only writer of a thought's phase and status and of a session's state. `state::apply` takes an open transaction, one event and the time, and returns the effects the caller carries out after committing: route, hold, launch, deliver, kill, settle, notify, answer. It does no I/O and reads no clock. Every effect that spawns something is preceded by its attempt, written with a hash of its arguments, so a repeated call never spawns twice. The launcher and the router are traits with fixtures, for Phase 2 and 3 to fill. `tests/state.rs` proves every row of the table, every guard and every recovery rule, and feeds every event to every state reachable in seven steps.

It also builds the binary `tasktap`, whose role so far is the service: `tasktap serve --data <folder>`. One core serves a folder, held by the lock `core.lock`; a client that finds none starts it and waits for its `ready` line (`src/client.rs`). It listens on `core.sock` (a named pipe on Windows) for peers of the same user only, answers `hello` (`src/handshake.rs`), authorizes every call in one place and runs it from one table (`src/calls.rs`), bounds each connection (`src/conn.rs`), and exits a minute after the last client left and the last hold ended, or when asked with `core.retire`. Platform code lives in `src/sys.rs` alone. `tests/service.rs` starts the real binary and proves each promise; the binary's test hooks (`--idle-ms`, `--fixture-token`) exist only with the `fixtures` feature, which only the tests turn on.

Records (`src/records.rs`) are how every client sees state. `sub` names whole collections and gets a snapshot at revision R, in chunks of at most 256 KiB, then every committed change after R that touches them, fanned out on the write path in commit order (`Core::publish`). `put` and `delete` write the plain data: preferences, layouts, a project's editable fields, a note's text and strokes. `history` pages back the thoughts that left the live set. `glance` lives in memory, takes its revisions from the same counter and starts over at every run (`Core::set_glance`). `tests/records.rs` proves it; rows only the state machine writes come from the test-only call `fixture.records`. The protocol crate bounds every text a call writes into a row (`MAX_TEXT`, `MAX_LINE`, `MAX_POINTS`) and refuses more as `invalid`, so with every field at its limit a row still fits one chunk; `tests/limits.rs` proves it.

Streams (`src/stream.rs`) carry raw bytes. Only the core opens one, as the reply to a call; each side grants the other byte credit, at most 4 MiB outstanding, and bytes beyond a grant end the connection. Inside the core the far end of a stream is an endpoint, asked for bytes only while the client has credit and its socket keeps up, so a reader that stops costs nothing and nothing piles up in the core. A terminal is the endpoint from Phase 2; until then `fixture.stream` sends and takes known bytes. `tests/streams.rs` proves it, and `scripts/measure.sh` measures its rate.

The calls with effects (`src/effects.rs`, `src/questions.rs`) put the state machine to work. Each thought, session and question call becomes one event, applied, committed and published in one step; the effects it returns then go to the router, the launcher, the hold timers (one one-shot timer per held thought, and nothing else is ever armed), the host and the waiting askers, and what they report comes back as events. A session's token names its session: `session.event` and `question.ask` never take it from their arguments. A `question.ask` call is its question's waiter and its reply is the stored answer; a waiter that disconnects withdraws its question, asking again with the same key reopens it or returns the answer stored meanwhile, and `question.received` marks the receipt delivered. `glance` follows the rows each commit sends. A build without the test fixtures has no router and no launcher yet and refuses what needs them with `failed`; with them, `fixture.script` selects and scripts the state machine's fixtures and `fixture.clock` holds the core's clock, so no test waits for a hold. `tests/questions.rs` proves each call, each refusal and every cell of the lifetime table in design §6. `tests/loop.rs` is the loop check every phase must keep passing (§13): capture, route, hold, launch, ask, answer, finish, restart, with a client holding the session token standing in for the agent until Phase 2.

Prove it from this folder:

    cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test --workspace

`BLESS=1 cargo test -p tasktap-proto` regenerates `protocol.ts` and writes missing samples. It never rewrites a sample that exists: the bootstrap samples are frozen.

The specification is [docs/core-design.md](../docs/core-design.md): §1 and §2 for the protocol, §3 and §5 for the store, §6 for questions, §14 for the build order.
