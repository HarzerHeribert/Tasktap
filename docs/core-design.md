# Tasktap core design

Written 2026-11-17, revised the same day after two reviews. It follows [rebuild-plan.md](rebuild-plan.md) and uses [rebuild-inventory.md](rebuild-inventory.md) ("inv. §n", "hazard n") as the description of 1.2. A line marked **Changes the plan** departs from the plan's wording. The core is built on its own first; the 1.2 app is not wired into it and keeps working untouched until cutover (§14).

## Summary

1. The core is one small program, written in Rust, that owns everything that is not pixels: the data, the terminals, the agents, the questions, routing and cloud speech.
2. All data lives in one database file that only the core writes. Windows keep nothing. The notch therefore works when the workspace was never opened, and clearing a window's storage loses nothing.
3. Everything that talks to the core uses three ideas and no others: **records** a client can watch, **calls** it can make, and **streams** for terminal bytes. Today about 235 kinds of message, command and file do this work.
4. The same program is also the small tool agents run to say "I started", "I have a question", "I am done". Their reports arrive the moment they happen, so nothing looks at files on a timer any more.
5. The main record is the thought, with one status. One table of rules, in one place, decides every status change. Today four parts of the app write the same status field.
6. An agent's question and a routing question are the same record and the same answer card. An answer is stored before it is sent, and can settle only the question it was shown for.
7. When nothing happens the core does nothing at all: no timers, no wakeups, under 8 MB of memory.
8. Sessions survive closing and quitting the app. An update never ends running work. After a crash or restart nothing starts again by itself.
9. The core is built and proven by itself first. The new notch and workspace are then built on it. Data from 1.2 is copied in once at cutover; the old files are only read.
10. Every window and tool identifies itself, and what each may do is decided call by call. Controlling a core on another machine later adds to the protocol without changing what exists.

## 1. Shape of the protocol

Commands and host abilities are the same mechanism pointed in different directions, so there are **three** mechanisms, not four.

| Mechanism | What it is | Covers |
| --- | --- | --- |
| **Records** | A connection subscribes to whole collections. It gets a snapshot at revision R, then every later change in order. Rows arrive whole. The core is the only writer, so there is nothing to merge. | all state: what `shared-state`, the 50 entry points and every "status" query do today |
| **Calls** | `call {id, name, args}` → `reply {id, ok \| err}`. Any side can call another: pages and tools call the core; the core and the pages call `host.*`; the host calls `ui.do`; the core calls `shim.hold`. One name table, one error shape. | every action, and every host ability |
| **Streams** | Numbered byte channels opened by a call. Raw binary frames with byte credit in both directions. | terminal output and input, file and preview bytes, dictation audio |

```ts
type Frame =                                   // kind 0: one JSON object
  | { t: "hello"; v: [min: number, max: number]; role: "page" | "host" | "cli"; client: string;
      auth?: { device: Id; key: string; register?: { name: string } } | { token: string }; abilities?: string[] }
  | { t: "welcome"; v: number; core: Id; build: string; as: "device" | "session" | "none"; calls: string[] }
  | { t: "refuse"; why: "auth" | "revoked" }
  | { t: "call"; id: number; name: string; args: object }
  | { t: "reply"; id: number; ok?: unknown; err?: { code: "unknown" | "invalid" | "denied" | "conflict" | "gone" | "failed"; message: string } }
  | { t: "change"; rev: number; snap?: true; more?: true; sets: { c: Collection; put?: Row[]; del?: Id[] }[] }
  | { t: "credit"; s: number; n: number }      // grant n more bytes on stream s
  | { t: "mark"; s: number; at: number; size?: [cols: number, rows: number]; live?: true; gap?: true; from?: number; exit?: number | null }
  | { t: "close"; s: number; why?: "done" | "overflow" | "gone" | "denied" }
// kind 1: stream bytes = u32 stream id, then raw bytes
```

**Subscriptions.** `sub {collections}` is the only form: no filters, no limits, one subscription per connection (a second `sub` replaces the first; an empty list ends it). The core answers in one step on its single thread: the snapshot as `change` frames marked `snap` (chunks of at most 256 KiB), then `reply {rev: R}`, then every change after R that touches a named collection. Nothing can fall between the snapshot and the first change. The snapshot is read and encoded in that step but sent at the pace the connection drains, like stream data; everything queued for the connection meanwhile, later changes and replies, waits behind it in order. One `change` is one committed transaction, so a client never sees half of it; one too large for a frame is cut like a snapshot, into frames with the same `rev` in a row. In both, every frame but the last is marked `more`, so a client applies a transaction whole when its last frame arrives. Memory-only collections use the same counter. Revisions order changes within one run of the core; a client always starts from a snapshot.

**Live rows only.** Collections hold what is live. A thought is live until it is finished (done or failed, read, settled) and 200 newer finished thoughts exist; its sessions, questions and results are live with it. A row that stops being live is a `del` in the change that caused it. Older thoughts are fetched with `history {before?, after?, limit ≤ 100}`, which returns them with their questions and results in pages whose rows fit one chunk; a page cut among one thought's questions and results names in `after` where the next goes on. They are not subscribed. This bounds every snapshot. I found no case that needs more.

**Plain data and effects.** `put {c, id, patch, if_rev?}` and `delete {c, id}` write the collections that are plain data (`prefs`, `layouts`, `previews`, the editable fields of `projects`, and the text of a thought that is captured and was never launched: a note, an idea, or one undone before it started, which `delete` also removes, so a person who undoes and retypes leaves nothing behind; `state::plain` decides). Everything with an effect is a named call. Fields the state machine owns are refused by `put`.

Calls without a mark are built in Phase 1; (2) and (3) name the phase that added the rest; "not built" marks those no phase has added yet. The protocol crate holds only what exists: the 39 built (`core/proto/src/call.rs`, whose test holds this table to them).

## 2. Framing, transport and trust

| Topic | Decision | Reason |
| --- | --- | --- |
| Transport | Unix socket `<data>/core.sock` (mode 0600 in a 0700 folder) on Mac and Linux; an owner-only named pipe on Windows | The plan's private local channel. No loopback TCP: any local program or web page could reach it. |
| Framing | `u32` length (little-endian, counts kind and payload), `u8` kind, payload. Kind 0 is one JSON object in UTF-8, kind 1 is a `u32` little-endian stream id and raw bytes. At most 1 MiB per frame, 64 KiB per data frame. Call ids are `u32`, unique among the caller's pending calls. Revisions and byte offsets are JSON integers below 2^53. | Terminal bytes travel raw: no base64, no escaping, one copy. Control stays JSON, so it is readable and the TypeScript types are generated. Rejected: WebSocket locally; a binary format for control. |
| Streams | Only the core opens a stream, as the result of a call. The caller's args carry the credit it grants for bytes toward it; the reply carries the stream id and the credit the core grants the other way. `credit` adds to a grant, up to 4 MiB outstanding. Either side ends a stream with `close`; frames for a closed stream are dropped and its id is not reused on that connection. Bytes beyond the grant end the connection. | Real backpressure that also works over a slow link. Replaces the 15 s awaited-promise kill (hazard 11) and four different input caps (hazard 18). |
| A client that leaves | A connection ends when the client's end of it has been read to its end, or when the core closes it. Everything a client sent before it left is taken, a call, a reply or bytes for a stream, whatever the core was sending it at that moment. The core can learn that a client left from a write that fails before it has read what the client sent last: it then stops writing, drops what was queued for that client, queues nothing more, and reads on to the end. | A client may type and close at once. One that did lost what it typed whenever the core's next write found it gone first; on Windows that write was the console's repaint for the size the client had just given the terminal, and it failed with "the pipe is being closed" a few microseconds after the client's last bytes arrived unread. Found on Windows CI, where a test's agent then never got its line; the same on Mac and Linux under load (broken pipe). |
| Bounds | Per connection: 8 MiB of queued control frames (the snapshot being sent does not count, what waits behind it does, so a slow subscriber holds at most one snapshot and 8 MiB), 64 pending calls, 64 open streams. Per terminal: 8 queued chunks from its reader thread, which then waits. At most 256 connections; one that has not said `hello` within 5 s is closed, and at capacity the oldest of those makes room for a new one. No row is larger than one snapshot chunk: the store refuses a transaction that would write one as `invalid`, and each call bounds the texts it writes, which fails earlier and says which. A client over a bound is disconnected; memory never grows to suit a client. | Every queue has a bound. |
| Version | `hello` offers a range; `welcome` names the highest shared integer and lists the call names this core supports, so a newer app disables what an older core lacks. Additions do not bump the version. | A new app can drive an old core that still holds terminals (§3). |
| Bootstrap contract | Frozen forever: the frame layout, `hello.v`, `welcome.v` and `build`, `refuse`, and the calls `core.status` (build, versions, live terminal count) and `core.retire`. With no shared version, `welcome` says `v: 0` and only those two calls work, and they need the local user check and nothing else. With a shared version `core.status` is still anyone's and `core.retire` a device's alone. | Any app can ask any core what it is and ask it to retire; an agent, which holds only a session token, cannot end the core and every terminal in it. |
| Local peer check | On accept: the peer's user id must equal the core's. The data folder must be 0700 and owned by the user, as today. | Keeps today's protections. |
| Device identity | Each host has a row in `devices` and proves a 32-byte key, stored hashed. A local peer that passed the user check may register itself. `device.revoke` drops its connections at once. Pages use the host's connections. | Identity that can be listed and revoked. A program running as the same user can read the data folder anyway, so the key is identity, not a wall. |
| Session tokens | Each terminal the core starts gets a random token in its environment (`TASKTAP_SOCKET`, `TASKTAP_TOKEN`), stored hashed. `TASKTAP_SOCKET` is `<data>/core.sock` on every system; on Windows it only names the folder the pipe's name is made from. | Replaces the per-launch observer token. |

**Authorization is per call.** The core takes the session, the terminal and a question's source from the token, never from arguments.

| Caller | May call |
| --- | --- |
| Device | everything except the token calls below. Only a device may call `question.answer` or `input`. |
| Session token | `session.event`, `session.adopt` (a shell's token), `question.ask`, and `question.withdraw` and `question.received` for its own questions. Nothing else. |
| Nobody | the abilities (`shim.hold`, later `host.*` and `ui.do`): the core calls them on a client that offered them in `hello`. |
| Local peer with neither | the bootstrap calls, and registering a device. Tools outside Tasktap's terminals get nothing more: other apps' sessions are cut. |

**Other machines, later.** Three additions, none of which changes a frame above: a second `auth` variant that proves a public key, a one-time pairing call, and a relay that carries these same frames between a device and a core that both dial out. Snapshots make reconnects cheap, credit handles latency, and `host.*` calls go to the remote device's own host. None of it is in the Phase 1 types.

## 3. Process model

| Topic | Decision |
| --- | --- |
| Lifetime | Runs while any client (a connection that said `hello`) is connected, any terminal is alive, a hold timer is armed, a model is asked about a thought (§8) or git work for a worktree runs (§7, "Isolation"). When all become false it arms one 60 s timer and exits when it fires. |
| Single instance | An exclusive file lock on `<data>/core.lock`, held for life. A second `serve` exits 0. The lock, not the socket file, is the truth. |
| Start on demand | A client that finds no socket starts `tasktap serve --data <dir>` detached and waits on a pipe for the `ready` line the core writes once it listens. No retry loop. The data folder is always passed; there is no default path (hazard 7). Many clients at once start one core and all get in, waiting for each other on `start.lock` in the kernel: each holds it shared from before it connects until it is welcomed; a starting core holds it alone until it listens. A client that finds no core, or is refused because the listen queue is full (128 on macOS, which refuses at once rather than waiting), takes it alone, which it gets once every client connecting before it is in, and connects again; only when no core holds `core.lock` does it start one, with `--locked`, keeping the lock until it listens. A core that idles out takes `start.lock` alone first and keeps it until it is gone, so no client is left in its queue; with a client connecting it stays. |
| Where it runs from | A copy at `<data>/bin/<build>/tasktap`. Windows cannot replace a running program, and hooks of running sessions keep pointing at the build that started them. Unreferenced builds are deleted at start. |
| Effects happen once | Every call that starts a process names an attempt id. Before spawning, the core commits the attempt with a hash of its arguments. The same id with the same arguments returns the first outcome; with different arguments it is `conflict`. When what was spawned cannot be stored, the core exits non-zero instead of answering, and the next start closes the attempt as `interrupted`. Creates are idempotent on the client-minted id in the same way: each is recorded as an attempt under its id with a hash of all its arguments, checked before anything else. |
| Crash recovery | At start, in one transaction: an attempt with no recorded outcome is `interrupted`; terminals marked running by an earlier boot become `lost`, their sessions `ended`, their thoughts `failed (interrupted)`, their open questions `withdrawn`; so does a session whose terminal a clean shutdown ended (§9). Hold timers are not restored, and none fires once a shutdown has begun: a held thought stays `routed` with no timer and waits for the person to press Start. A router that was being asked about a thought (§8) is not asked again: the thought stays as it was, its `route` no longer pending and saying why. Then, before the first connection is taken and off the core's thread, the worktrees are swept (§7, "Isolation"): a settle the core stopped during is decided only where it left nothing, and nothing is removed but what git itself agrees is empty. |
| Never rerun | There is no queue to drain and recovery only closes things. A launch happens only inside a call from a live client. The 1.2 start-up relaunch of jobs without receipts (hazard 12) is gone. |
| Durability | SQLite in WAL mode with `synchronous=FULL`: a reply is sent after its transaction is on disk. Writes are state changes only. **Decided in package E, without `F_FULLFSYNC` on macOS** (`PRAGMA fullfsync` off, set so in the store). There `fsync` hands the commit to the drive, which may still hold it in its cache when the power goes; `F_FULLFSYNC` flushes that cache too. Measured by `core/scripts/measure.sh` (Apple M4 Pro, macOS 27.0.1, 500 commits each of a 400-byte row as the store writes one): `synchronous=FULL` alone 0.039 ms a commit (median; p95 0.049 ms), with `F_FULLFSYNC` 4.03 ms (p95 4.21 ms), a hundred times more. A commit runs on the core's thread, so every commit would hold up a keystroke by 4 ms, thirteen times the 0.3 ms the core may add; the stricter setting was worth it only at a negligible cost. What it buys is small: the records are small and rarely written, and a power cut that loses the last commits leaves an older consistent file that the recovery pass closes as for a crash. The script fails this row should `F_FULLFSYNC` ever cost less than 0.3 ms, so the choice is made again. While another client commits all along, the core adds 0.088 ms to a keystroke (§10). |

When a newer app meets a running core it calls `core.status`:

| Running core | Terminals alive | What happens |
| --- | --- | --- |
| Same build | any | Use it. |
| Older | no | `core.retire`: it exits cleanly, the app starts the new one. |
| Older, shared version | yes | Use the old core, with the calls it lists. `core.retire {when: "idle"}` makes it exit when its last terminal ends. `glance` reports the pending update; the UI shows "Finishes updating when running work ends" and "Restart now (ends N sessions)". |
| Older, no shared version | yes | The same two choices from the bootstrap contract, with the workspace waiting. Sessions are never ended without the button. |
| Newer than the app | any | Use it at the shared version. Never retire a newer core. |

Rejected: handing live terminals to a new process (Unix only, and it freezes an in-memory format). Rejected: launchd or systemd activation (a per-platform install step).

## 4. One binary, several roles

The binary is `tasktap` (the service is still "tasktap-core"). All roles but `serve` arrive in Phase 2.

| Role | Run by | Replaces |
| --- | --- | --- |
| `serve` | the host, or any client on demand | `workspace_terminal.py` (service and bridge), `run-agent`, `LiveWorkspace`'s runner, `QuestionInbox` |
| `hook <agent>` | an agent's hook, with the payload on standard input. The agent's adapter (§7) runs here, in this process: it maps the payload to one `session.event` in the core's vocabulary, to nothing, or to a question the agent lets the hook decide. Then the hook asks with `question.ask`, waits on the socket, prints the reply the adapter formats and confirms with `question.received`. **Changes the design:** the core never sees an agent's own payload, so one it would not understand never reaches it | `session_observer.py ingest` |
| `event <kind> [TEXT]` | an agent's plugin that can run a command: one `session.event`, `TEXT` in the field its kind has (for `continued`, the key of the waited question it settles), with `--id`, `--turn`, `--subagent`, and for a question `--request`, `--detail`, `--choice`, `--text` | `observers/emit.mjs` |
| `ask [PROMPT...]` | an agent in a Tasktap terminal, with `--request KEY`, `--detail`, `--choice` (repeated) or `--text`; without a prompt the first line of standard input is the prompt and the rest the detail. Sends `question.ask`, sleeps on the socket, prints the answer (`yes` or `no`, the choice, or the text), confirms with `question.received`. The same key asks once: again it gets the stored answer | `ask-user`, and the `agent-tools` MCP server (`report_result` becomes `event turn_finished`) |
| shim: the same file named `claude`, `codex`, … | a person typing the agent's name in a Tasktap shell | `tasktap_shell.py cli`, `Shells/<id>/bin/*` |
| `fixture-agent` | tests, and package C's loop in a real terminal; only in a build with the test fixtures. A scripted agent that prints, reports through its hook, asks and waits, reads a line, sleeps, ignores hang-up and exits with a code | – |

The roles use the blocking client and nothing else: no runtime, no store. `event` takes about 2 ms from start to exit against a running core. Each waits at most 5 s for the core, its lock or its agent's pipe; a question's wait lasts as long as its connection, which the core withdraws the question with. Exit codes: 0 done (for `ask` and a waiting hook, answered); 1 the core refused the call or the connection ended; 3 no answer, the question was withdrawn or its session has ended; 64 wrong arguments; 65 a hook payload the adapter cannot read, nothing sent; 69 no core reached or started in time; 77 the session token refused or malformed; 78 no session token, not in a Tasktap terminal. None is 2, which Claude Code reads as a hook blocking its tool.

**The shim** keeps the rules of `scripts/tasktap_shell.py`. The shim folder is `<data>/shims`: links (copies where links fail) of the binary named after each agent that has an adapter, and `tasktap` itself, which the hooks and `tasktap ask` run; a shell puts it first on its PATH. Every other terminal finds `tasktap` in the core's own folder instead, last on its PATH (§7). The shim finds the real executable on the PATH, skipping that folder and any file that is the shim itself. It steps aside (runs the real CLI directly, unobserved: `exec` on Unix) when input or output is not a terminal, for print, help, version and remote modes, for the listed non-interactive subcommands, when the core does not answer within 5 s, and when the terminal already has a live observed agent, which `session.adopt` reports as `conflict`. Otherwise it calls `session.adopt` on a connection that offers `shim.hold`, adds the hooks (the adapter's `attach`) and what the adapter's probe adds, run with the agent it found (an agent whose probe fails runs unobserved), adds the default approval flag only if the person gave no policy of their own, starts the real CLI as its child, ignores Ctrl-C while it waits, restores the terminal modes, and reports the exit as `session.event exited` on a second connection. It stays the parent because the core parents only the shell, and so it is the one that ends its agent when the person stops the run (`shim.hold {stop}`, §7). The links are symbolic on macOS and hard elsewhere: a hard link gives the binary a second name, and macOS, which reads each program it starts to check it, may then look for it under one link's name in another link's folder, find nothing and kill it, a shim or the binary under its own name alike (`tests/roles.rs`). The adopted session belongs to the adopting connection: when that ends first, a shim killed, the session ends with no exit code.

Improvements on the hypothesis: (1) **a hook can wait**, so a question can be answered from the notch where the agent allows it (§6); (2) **no wrapper for agents the core launches**: the core is their parent and knows start and exit itself, so `present`, `surface.json`, three lock files and three sources of `process_exited` go; (3) **no MCP server**: `tasktap ask` is an ordinary command; (4) **activity is not written to disk**, only state changes are. This removes the 0.7 s receipt poll, the 8 s scan, the 0.2 s answer poll and every run-folder file.

## 5. Data model

One SQLite file, `<data>/core.db`. Ids are UUID v7 text, minted by whoever creates the record; the core mints its own on its clock, which tests may hold. Every row has `rev`. `PRAGMA user_version` is the schema version; migrations are an ordered list of SQL in the binary, applied in one transaction after a backup made with `VACUUM INTO`; a database newer than the binary is refused with a clear message.

**Core id.** `meta.core_id` is minted once. `welcome` names it, so a client can hold records from several cores. It is not a column on every table: a value that is the same in every row is not data. References never cross cores.

### One state machine

Only `state::apply(event)` writes a thought's `phase` and a session's `state`, apart from the store's recovery pass at open (§3). A thought's **status** is derived in the same transaction: **needs you** while the thought has any open question, otherwise its phase (captured, routed, working, done, failed). A session shows `asking` by the same rule. So answering one of several questions does not clear needs you. Event names are the observer's (inv. §5.3). The receipt, row and JS vocabularies (Opening, Opened, Closed, Copied, Delivered, Complete, Connected, Queued, Saved, Last seen, Awaiting agent) are dropped.

**How a thought came by its place** is its `placed`, one word of a closed set, written by the state machine in the step that places the thought or keeps it for later. A question asked in the terminal arrives as such an event and passes the same guards.

## 6. Questions

One record and one flow replace the file inbox (path A) and the observer display (path B).

1. **Ask.** A question is opened by the core's router, by `question.ask` from `tasktap ask`, or by the adapter reading a `session.event`. Its `source` says who asks: an agent's permission request that a hook waits on asks with `source: permission`; without one it is `agent`; only the router's own questions are `router`, which a session asking is `invalid`. It is idempotent on `request_key` (for `ask`, the session and its `request` argument; for a hook, the session, turn and the agent's own call id): the same key with the same content is the same question; different content is an error. The key is per session, so one session's token never reaches another session's question. A request never changes. A session holds at most 8 open questions and all sessions together 64 (`MAX_SESSION_QUESTIONS`, `MAX_OPEN_QUESTIONS`); beyond that a new one is `conflict` until one closes.
2. **Show.** The thought's status becomes needs you, `glance` changes, the core calls `host.notify`. `glance.question` is the focused question (the one that opened first, by the revision it opened at rather than its id, unless `question.focus` chose another), so a host can bind the affirm and deny keys with no page running.
3. **Answer.** `question.answer {id, …}` or `input {answer.affirm | answer.deny, question}`, from a device only. One transaction inserts the `answers` row (its key is the question id, so a question is settled once, and only by an answer that names it) and sets `answered`. Answering a withdrawn question is `gone`.

**Lifetime depends on who is waiting.**

| | Terminal-only question (`reply_via: terminal`) | Waited question (`reply_via: core`) |
| --- | --- | --- |
| Opened by | a hook that reports and exits | `tasktap ask`, or a hook that waits. The pending call is the waiter |
| Bound to | its session and turn | that waiter |
| The card | shows the question and "Answer in terminal", which opens that terminal. Affirm and deny do the same | answers it. Affirm and deny act directly on `confirm` and permission questions |
| Closes | on `continued` (answered, kind `terminal`), or withdrawn at turn end or session end | when answered, or when the agent went on from it in its terminal (`continued` naming it; answered, kind `terminal`): the stored answer is the call's reply; the waiter prints it and sends `question.received`, which sets `delivered` |
| Waiter disconnects | – | withdrawn at once. If the waiter comes back with the same key while the turn is alive, the same question reopens, or, if it was answered meanwhile, the stored answer is returned again |
| Never delivered | – | the answer stays stored with `delivered` empty and the card says so; turn end closes it |

Nothing waits forever (hazard 10). Merged or dropped: `discussion[]` and the discuss key become a text answer (today the first discussion line already ends the agent's wait); `binary` becomes `confirm`; `producerKey` becomes `request_key`; `reconcileAgentQuestions` becomes withdrawal.

## 7. Agents

```rust
trait Agent {
    fn id(&self) -> &'static str;                                  // "claude": the shim's name, `tasktap hook <id>`, a capture's `agent`
    fn program(&self) -> &'static str;                             // looked up on the terminals' PATH
    fn caps(&self) -> Caps;
    fn launch(&self, run: &Run) -> Vec<String>;                    // a new run's or a resume's command line: the program, then its arguments
    fn attach(&self, exe: &Path) -> Vec<OsString>;                 // arguments that make a run call `<exe> hook <id>`; launch and shim
    fn probe(&self, exe: &Path, cwd: &Path) -> Option<Probe>;      // a check that must pass before the spawn; none for most
    fn detect(&self) -> Detect;                                    // its own commands that say installed, signed in, as whom
    fn headless(&self) -> Option<Headless>;                        // how its tool answers one question without a session (§8); none: it routes nothing
    fn told(&self, brief: &str, words: &str) -> String;            // what a run reads when a brief was written: the brief, then the person's words, marked
    fn variables(&self) -> &'static [&'static str];                // of the core's environment, what its runs need: a sign-in key
    fn prompts(&self) -> &'static [Prompt];                        // what it waits on in its terminal before it is ready: words shown, question
    fn event(&self, args: &[String], payload: &[u8]) -> Result<Option<Heard>, String>; // runs in `tasktap hook`: payload → the one vocabulary
    fn reply(&self, args: &[String], payload: &[u8], answer: &Answer) -> Option<String>; // what a hook that waited prints; none leaves it to the agent
}
struct Caps { events: bool, resume: bool, permissions: Option<ReplyVia>, questions: Option<ReplyVia> } // events false: it reports only by exiting, and exit 0 is done
struct Run<'a> { session: SessionId, cwd: &'a Path, prompt: &'a str, words: Option<&'a str>, model: Option<&'a str>, resume: Option<&'a str>, hook: &'a Path } // words: the person's own, when prompt is a brief of them
struct Headless { tool: &'static str, model: &'static str, limit: Duration, args: fn(&Schema) -> Vec<String>, answer: fn(&str) -> Result<String, String>, gone: fn(&str, &str) -> bool } // the question goes to its standard input; answer finds the JSON in what it printed; gone: what it printed and last said mean it no longer offers the model
struct Detect { version: &[&str], version_of: fn(&str) -> Option<String>, account: &[&str], account_of: fn(Option<i32>, &str) -> (Option<bool>, Option<String>) }
struct Probe { argv: Vec<String>, input: String, read: Box<dyn FnMut(&str) -> Option<Result<Vec<String>, String>> + Send> } // what it adds follows the program
enum Heard { Event(SessionEvent), Wait(Ask) }                      // report and exit, or ask and wait: the agent lets the hook decide
```

An adapter is data and small pure functions: `event` and `reply` do no I/O and run in the `tasktap hook` process (§4), not in the core. What must run a program the adapter describes and `agents::checks` runs, on a thread of its own, with the terminals' fixed environment and PATH: `detect`'s two commands (4 s each) answer `agents.detect {agents?}`, which lists for each agent whether it is installed, its version, whether it is signed in and as whom, and its caps; `probe` runs before a launch (12 s at most). What detection finds is also kept in the `agents` collection, in memory, one row per agent keyed by its id: the fields `agents.detect` returns, with `rev` and `checked`, the time its commands answered. The core detects every agent once as it starts, off its thread and after `ready`, so a page shows them at once; `agents.detect` puts again the rows it found, and its reply is those rows. Nothing repeats it, and the detection keeps no core alive: one that idles out meanwhile ends without the rows. A build with the test fixtures detects at start only with `serve --detect`, and then only the fixture agents, so no test runs a real agent's commands. A launch answers its call at once: its program is looked up on the PATH and its probe run on a thread of their own, since a folder of the PATH may be on a stalled mount, and its outcome reaches the thought's record and the attempt once they have answered (the same `thought.start` repeated meanwhile is `conflict`, as for any attempt without an outcome). The agent's resume handle comes in its reports (`session.event` `resume`), and the session keeps the latest. The token is not the adapter's: the terminal puts it in every child's environment, and both tools pass their environment on to their hooks. An adapter declares the few variables of the core's own environment its runs need (`variables`): Claude Code `ANTHROPIC_API_KEY`, `CLAUDE_CODE_OAUTH_TOKEN` (the token `claude setup-token` makes for a subscription) and `CLAUDE_CONFIG_DIR`; Codex `OPENAI_API_KEY` and `CODEX_HOME`. So a person who signs an agent in through one is not signed out in Tasktap. Every terminal and every check gets them as the core had them at start, and no value reaches a record or a log. Hooks and settings travel as arguments, and nothing is written to `~/.claude` or `~/.codex`.

`core/src/agents.rs` holds the trait, the registry, the one list that names agents (its first is the default), and the test agents `fixture`, `fixture-silent` (no hooks) and `fixture-probed` (a probe), all the program `fixture-agent`, this binary under that name. `agents/claude.rs` and `agents/codex.rs` are the adapters; `agents/rules.rs` holds the shim's rules (§4) of the agents with an adapter, the only ones a shim is named after, so that an agent without one runs as typed; `agents/checks.rs` runs detection and probes. No other module names an agent.

**Which agent a run uses. Decided in package D.** The capture names it: `thought.capture {agent?, model?}`, an id `agents.detect` lists, `invalid` when this build has none of that name; a dictation's `thought` target carries the same capture, and is checked the same way before anyone speaks and again when its words are captured. The agent a capture names runs the thought or nobody does: when its row of the `agents` collection says it is not installed, or not signed in, the capture is refused, `failed` with "… is not installed on this computer" or "… is not signed in", and nothing is stored; it is never run by another agent. The collection is what the interface shows too, so both go by what detection last found, and `agents.detect` looks again; while no detection has finished, or the agent would not say whether it is signed in, the capture is taken, and a run that cannot start fails and says why. A capture that picks a session is not checked: a follow-up keeps its session's agent, whatever it names. Without one, the `agent` preference (none by default, passed over when it names an agent this build lacks), else the registry's first, Claude Code. The thought keeps its agent and model; a follow-up uses its session's agent, and a resume keeps its conversation's model. A model is 1 to 250 characters, none a control, not starting with `-`, as 1.2 checked it. In the tests, the agent `fixture.script` names comes before the preference.

Three things are the same for every agent and therefore not in the adapter.

**Environment.** The core builds each child's environment from a fixed list (home, user, language, shell, the computed PATH, terminal variables, `TASKTAP_*`, and the variables the adapters declare, above). Nothing else is inherited from whichever process started the service (hazard 14). The hooks run the core's program by its absolute path; `tasktap ask` runs by name, so every terminal finds `tasktap` on its PATH: a shell in the shim folder, first, so that an agent typed there is adopted; any other terminal in the core's own folder, last, so that it has no shim at all and nothing needs installing.

**Launching** (`core/src/launch.rs`). The launcher asks the adapter for the command line, runs its probe first if it has one (above), looks its program up on the PATH the terminal will have (a program that is not there fails the launch before anything starts), refuses a project that is closed, and starts the agent through `terminal::spawn` as the direct child of a new terminal of kind `agent` in the folder the launch names, with no shell around it. The terminal takes the session's id, as the session takes the attempt's, and the caller stores its row with the token's hash in the transaction that applies `launched`, before anything else runs, so an id the store knows is never started twice. The hooks call the core's own program. When the child exits its session gets `exited` with the code at once, `silent` when its adapter reports no events; an adopted agent's shell is never silent, as its shim reports the agent. `thought.stop` stops the run's terminal (never a shell); for an agent adopted in a shell the core calls `shim.hold {stop: true}` on the adopting connection, and the shim hangs up on its agent, kills it 2 s later if it is still there (on Windows ends its process tree), and reports its exit, leaving the shell. Only the agent is signalled: what it started in its own process group outlives that, as from a shell. A run in a worktree has it made or found first, off the core's thread ("Isolation" below), and its probe and agent then run in it.

**Follow-ups.** A follow-up is typed into a terminal (bracketed paste, then Enter; its text keeps no control character but its line breaks and tabs, a carriage return becoming a line break, so nothing in it can end the paste, start another sequence or make the terminal interrupt, suspend or end the agent's input) only when that terminal's direct child is the agent the core launched, the session is not ended and the child has neither exited nor is being stopped. Then no shell exists underneath that could execute the text. Otherwise nothing is typed and the follow-up fails with the reason as its failure result. For an adopted session (an agent started by hand inside a shell) the follow-up is typed only while the shim holds the terminal, and otherwise fails, its text left to paste. The core calls `shim.hold {hold: true}` on the adopting connection, if it offered the ability; the shim answers once it has checked its child is alive and its process group owns the terminal's foreground, or `gone`. The core then checks for itself, since anything the shell runs has the shell's token and could adopt and say yes: the process at the other end of the adopting connection, as the system names it, must be in the group that has the terminal's foreground, and that must not be the shell's own; otherwise nothing is typed. Windows has no foreground group, so there a follow-up to an adopted session is not typed ("Verify when reached"). The core types the text and calls `shim.hold {hold: false}` only once the terminal's input thread has written all of it, or none of it is still to come: what the core types goes 256 bytes at a time, and past 5 s the core gives up on the rest, which is not written, and waits for the piece on its way. A follow-up is typed when all of it was written, and fails otherwise. A shim whose agent exits meanwhile reads its terminal into nothing, so the core's writing finishes, and waits for that call, or for its connection to end, at most 5 s, before it returns to the shell; it restores the terminal with `TCSAFLUSH` whenever a follow-up was typed during the run, so input the agent never read is discarded, not run, and none is still to come. The core waits 5 s for the answer. The follow-up's outcome reaches its thought's record, not the `thought.start` call, which answers once the hold is asked. This replaces `codex queue`, `pbcopy` and the Copied and Delivered states.

**Isolation** (`core/src/isolate.rs`, Phase 3). A thought can run in a git worktree of its own, so that two agents never write the same files and what one did comes back as changes the person keeps or discards. `state.rs` decides; `isolate.rs` does the git work and nothing else, on threads of their own, so the core's thread never waits on git.

| A new run | Works in |
| --- | --- |
| a follow-up typed into a live session | wherever that session works |
| a run of a thought that has a worktree it has not settled (a retry) | that worktree, made again on its branch where its folder is gone, and anew where its branch is gone too |
| a run that continues the conversation of an ended session that worked in a worktree whose changes wait | that worktree, which stays its owner's |
| a project that is no git repository (no `.git` in its folder: a folder inside a repository counts as none), or the scratch | the project folder |
| `isolate: never` | the project folder |
| `isolate: always` | a new worktree |
| `isolate: busy` (the default), while a session of the project starts or works, or a thought of the project has changes waiting to be kept or discarded | a new worktree |
| `isolate: busy` otherwise | the project folder |

**The promise, in three tiers.** Everything below follows from these three, and a change to isolation must leave each as checkable as it is.

1. **The person's own.** Tasktap never deletes or rewrites anything outside its own folder (`<data>/worktrees`) and its own `tasktap/` branches. The only effect it has on the person's project folder and branches is that a Keep adds the run's commits to a branch, by a fast-forward or one merge commit, and updates the files of a folder that has that branch checked out by the command the person would run for it, `git merge --ff-only`. That is as safe as that command, and no safer. Git refuses to write over an uncommitted change, an untracked file or an ignored one; but git checks and then writes, so an edit saved or a file staged in the instant between is lost, exactly as it is when the person runs `git merge --ff-only` or `git pull` at that moment. Tasktap adds no way to lose work beyond that. No code restores, resets, reads a tree into or deletes anything in a folder Tasktap did not make. Nothing a Keep did is ever undone, and its fast-forward is never ended part way: where something else happened than was asked, Tasktap stops, says exactly what is where, and leaves every branch and folder as git left them.
2. **Tasktap's own worktrees, as strongly as git makes it.** What is in a worktree under `<data>/worktrees` (the run's work) is removed only by the person's Discard, by a Keep that brought it into its destination, or on the core's own account when git itself agrees nothing is in it. The command that removes makes the check, not a look before it: every removal but a Discard uses the forms of git that refuse (`git worktree remove` without `--force`; the branch deleted by `git update-ref -d` with the old value, which is the commit the worktree started from, or the tip a Keep brought in, and never one read afresh), and the core's own removal first looks once for what those forms do not see: ignored files, and a HEAD that left its branch. What is written or committed after that makes the removal fail, not succeed. Accepted: a process that, in the milliseconds between that look and git's removal, writes an ignored file into Tasktap's own worktree, or takes its HEAD off its branch and commits there, loses that.
3. **Not a sandbox.** Tasktap runs git as the person's own git runs, with their configuration: filters (Git LFS among them), merge drivers, line endings and excludes apply as they do for the person. Hooks are off and every command has a deadline, so nothing waits on the person or hangs the core; a few settings that cost a line each keep git from asking, fetching or hiding what the core must read ("Git as the core runs it"). A program the person's configuration names does under Tasktap what it does when the person runs git. Guarding the person against their own configuration is not a goal: where it has git trace its commands to a file (Trace2), git writes that file under Tasktap as it does for them. Nor does Tasktap guard its data folder against being redirected while a job runs: that `<data>/worktrees` is a real folder of the data folder is checked once, when each job starts ("Removed").

**What writes outside `<data>/worktrees`.** Every git command the core runs is in `core/src/isolate.rs`. These are all of them that write anything there, and tier 1 is read off this list.

| Command | Run in | Writes | Why nothing of the person's is lost |
| --- | --- | --- | --- |

| `git merge --ff-only --no-overwrite-ignore --strategy=ort … <target>`, with `branch.<to>.mergeOptions` emptied | the folder that has `<to>` checked out | that folder's files and index, the branch it is on and its log, `ORIG_HEAD` | git's own fast-forward, the command the person would run, and as safe as that (tier 1): git refuses before it writes anything when the branch would not only gain commits, or when an uncommitted change, an untracked file or an ignored one would be written over. Everything else reads (`status`, `diff`, `diff-index`, `rev-parse`, `symbolic-ref`, `merge-base`, `worktree list`, `var`), with `GIT_OPTIONAL_LOCKS=0`, so that the project folder's index is not refreshed (of a split index git may still touch the shared file's time, as any command of the person's does). Every command runs with `GIT_NO_REPLACE_OBJECTS=1`: a replacement ref changes nothing of what Keep takes a commit's history to be. Files are written only under `<data>/worktrees`: a worktree's folder is made there (never found), and removed whole only as `<data>/worktrees/<name>`, on a Discard or by the attempt that made it a moment before and failed. So no command takes anything from a branch that is not `tasktap/…`; the one command that writes the person's files is the fast-forward they would run, as safe as it is for them; and nothing follows it but the removal of Tasktap's own worktree and branch. Two commands can land elsewhere than asked, and both only add commits: the fast-forward, when its folder switches branch in that instant, which the reply reports (the table of Keep, below), and the commit in the worktree, when its HEAD is switched between the look and the commit, which gives the branch switched to that one commit.

- **Made.** A new worktree is `<data>/worktrees/<name>` on a new branch `tasktap/<name>`, the name the last 12 hex digits of the launch attempt's random end, from the commit the project folder's HEAD is at. Its owner records it before anything runs in it (`prepared`): the path, the branch, the destination (the branch the project folder was on; none on a detached HEAD), the base commit, and `left_out` when the project folder had uncommitted changes of its own. **Decided:** the run starts from what is committed, and the person's uncommitted work stays where it is, outside the worktree. Copied in, it would come back in Keep as the agent's work, committed into the person's branch while it is still uncommitted in their folder, which Keep must then refuse. `left_out` lets the interface say so. The folder is made by that attempt alone (made, never found), and the branch is made only where none of that name is (`git update-ref` with no old value), so two attempts that come to one name, or a branch the person made meanwhile, stop the second attempt, which touches nothing it did not make. A repository with no commits, a folder or branch of that name that exists (never touched), or git failing fails the launch with the reason, and what that attempt made is removed: its folder, in which nothing has run, and its branch only while it is still at the base. The worktree has the repository's submodules as empty folders, as `git worktree add` leaves them, and nothing is cloned. A file a filter applies to is checked out through it, as in the project folder: Git LFS takes it from the repository's own store, and fetches what is not there within the command's deadline. The probe and the agent then run in it.
- **A worktree belongs to one thought,** its owner. Follow-ups to its sessions work in it; only the owner settles it; no run starts in it while a settle of it runs.
- **Looked at.** When a turn ends, or a session ends, in a worktree, the core looks at it: the files, lines added and lines removed against the base, committed on the branch or not, untracked files included, read through an index of the look's own so the agent's index is left alone; and whether removing it would lose nothing (below). The changes are `none` only then, and `pending` otherwise, even with no file changed: something staged that the files no longer show, an ignored file, or a folder git no longer ties to its branch (its `.git` names git's record of it, which names it back, and its HEAD is on `tasktap/<name>`) is the person's to keep or discard. `thought.changes {id, credit, path?}` reads the same: its reply lists the files (path, added, modified, deleted or type, lines; as many as fit 256 KiB, `more` counting the rest) and opens a stream of the diff as `git diff` prints it, at most 4 MiB (`MAX_DIFF`; `size` and `cut` say when there is more), the whole or one file's. At most 4 diffs are held at once.
- **Tidied.** A worktree whose changes are `none`, once no session and no terminal works in it, is removed with its branch on the core's own account (a tidy, an attempt of kind settle), as tier 2 says. First one `git status` there, which must show its HEAD on its branch at the base, with nothing staged, changed, untracked or ignored. Then `git worktree remove`, which checks for itself that the folder is the worktree git knows and holds no change and no untracked file (`status.showUntrackedFiles=normal` is set on the command, so no preference of the person's hides one from it). Then the branch, deleted only from the base. One that holds something after all, or that git will not remove (a `git worktree lock` of the person's, submodules the run filled), stays whole, and its changes become pending: the person's to keep or discard. A commit made after the folder was found empty leaves the folder removed and the branch with that commit, pending. One in use stays as it is until a later look.
- **Removed** only when proven the core's own. First `<data>/worktrees` itself: a real folder, no link, at its place in the data folder, or the job does nothing there, the start's sweep included, and says why. Then the folder: exactly `<name>` inside the canonical `<data>/worktrees`, the name one the core makes (12 lowercase hex digits), reached through no link, and the record's branch `tasktap/<name>`; a record naming anything else is refused before git runs, whatever the store holds. Never while a process works in it or below it, whatever the process is: the upkeep git leaves running for a moment after a commit of the agent's counts too, and a removal pressed in that moment refuses once. On Linux and macOS the core reads the working folder of every process (`/proc/<pid>/cwd`, `proc_pidinfo`); a process of one of the core's terminals whose working folder the system does not show counts as working there; and where the processes cannot be listed at all, what the person asked for goes on and the core removes nothing on its own account. On Windows a folder a process works in, or holds a file of, cannot be renamed: the worktree is given another name (`<name>.probe`) and its own back at once, and is in use when that fails; one a core that stopped left under the other name gets its name back at the next start. A Discard then removes the folder whatever is in it (links inside are removed, never followed), then git's record of it. A Keep and a tidy have git remove it (`git worktree remove`), which refuses a folder that is no longer its worktree or that holds a change or an untracked file. The branch goes last, and only from a commit that was proven (`git update-ref -d` with the old value): the base for a tidy, the tip a Keep brought into its destination, the tip read before anything was removed for a Discard. A branch `tasktap/<name>` is Tasktap's wherever it is: one the person checked out in a folder of their own, once its worktree was gone, is deleted all the same, which leaves that folder's files and index as they were, on a branch with no commit. No folder is removed for its name, and no start finishes a removal: one that stopped midway left what git shows, which the next look reads.
- **Settled.** `thought.settle` needs the changes pending and no session and no running terminal of the core in the worktree: an agent stopped is not enough until its process has gone. Otherwise it is `conflict`; the interface confirms, stops the session and asks again. No agent is adopted into a worktree while it settles. The reply waits for the git work. A removal that finds a process working there, a shell that went there by `cd` included, refuses: a Discard has then removed nothing, and a Keep has kept and says that the worktree stays.

| Keep, when the destination | |
| --- | --- |
| has not moved since the base | fast-forwards to the branch |
| moved, and both merge without a conflict | gets a merge commit of both, made without a working tree (`git merge-tree --write-tree`, `git commit-tree`; git 2.38 or newer), and fast-forwards to it |
| moved, and they conflict | refuses: names the files, leaves everything as it was, and says that branch `tasktap/<name>` holds the changes to merge by hand; Keep after that finds it merged and only tidies up. A merge driver the person configured decides as it does for them |
| holds the branch already (merged by hand) | stays; Keep only tidies up |
| is checked out in a folder, the project folder or another worktree | moves with that folder, by `git merge --ff-only`, which git refuses before it writes anything when it would touch an uncommitted change or an untracked or ignored file (`--no-overwrite-ignore`), or when the folder is in the middle of a merge; the reply carries git's own words, which name the files. Where another git command moves the branch after git wrote the files, git leaves them written and the branch where that command put it, as it does for the person, and the reply carries that too. Every option that decides what it does is on the command (`--no-squash`, `--commit`, `--no-autostash`, `--strategy=ort`, no hooks, no signature check), and the branch's own `branch.<name>.mergeOptions` are emptied for it: no preference of the person's has it do something else. It is never ended: past 600 s the reply is that git is still updating that folder and nothing was stopped, the changes stay pending, and git finishes by itself. Afterwards the destination must hold the commit. Where it does not, the folder switched to another branch in that instant and git merged into that: nothing is undone, and the reply says which branch git merged into, that the destination is as it was, that `git reset --keep ORIG_HEAD` in that folder takes the commits out again, and that `tasktap/<name>` holds the changes, which stay pending; the next Keep goes on from what is there |
| is checked out nowhere | moves alone, from where it was (`git update-ref` with the old value). A folder that checked it out in that instant, still holding the old files, is not touched, and the branch is not moved back: the reply says that the changes are in the destination, names the folder, and gives the command that brings its files in without touching a change of the person's (`git read-tree -m -u <old> <new>`); the changes stay pending, and Keep again only tidies up. A destination that a folder is rebasing counts as checked out nowhere: it moves, and git stops that rebase at its end, where it finds the branch elsewhere than the rebase began |
| is gone, or was none (detached HEAD) | refuses; the branch is the person's |

Before that, Keep commits what is uncommitted in the worktree on its branch (`git add --all`: what git ignores there is not kept), once the worktree is still tied to that branch ("Looked at") and in the middle of no merge, rebase, cherry-pick, revert or bisect; refused later, the branch then holds all of it. On success the worktree and the branch are removed and the changes are `kept`. Where the worktree cannot be removed (a process works there, something new is in it, git will not), the Keep has happened all the same: the reply says that the changes are in the destination and that the worktree stays, the changes stay pending, and Keep again tidies up, as Discard does. **Decided:** a fast-forward when the destination has not moved, else a merge commit, because neither rewrites anything: the person's branch only gains commits, its history and their commits stay exactly as they were, a fast-forward keeps it straight when nothing happened meanwhile, and a merge commit is one commit that undoes as one. Nothing is rebased (that would rewrite either the person's commits or the agent's, whose tests then never ran) and nothing is forced.

- **Discard** removes the worktree, what is uncommitted or ignored in it, and its branch, commits that are nowhere else too, and marks the changes `discarded`. It never touches the project folder's files. It is how the person removes a worktree that would lose something or that git will not remove, one git no longer ties to its branch included. Where all of it was in its destination already (a Keep that left the worktree, a keep the core stopped during, a merge by hand; nothing uncommitted beside it), nothing is discarded, and the changes are marked `kept`.
- **At the same time.** `state.rs` lets one settle or tidy of a worktree run at a time and starts no run in it meanwhile; a look reads through an index of its own. The jobs of one core on one worktree take turns, a look too, each waiting for the one before, so that no git command of the core's own is at work in a folder another job asks about or removes. Nothing is locked against other processes: every command that moves or removes something is one of git's that checks for itself. On Windows, removing a folder is tried again for a few seconds, since a virus scanner holds a new file for a moment. **Decided:** the core does not end its git commands when it stops, since ending one midway may leave the person's index or files half written; the command finishes what it began, and the next look sees what it did. A Keep's fast-forward that outlives a core that stopped therefore completes after the restart, and should the person have discarded those changes in between, their branch has the commits although the record says discarded. Accepted: it is the Keep the person pressed, nothing of theirs is lost, and a lock held across processes to prevent it cost more than it protected.
- **Recovery.** The sweep at start (§3) looks at the worktree of every thought whose changes are not settled. A settle the core stopped during (its attempt `interrupted`) is decided only where it left nothing: with the folder and the branch both gone, a keep is `kept` and a discard `discarded`. Whatever it left is pending again (or none, where nothing is in it, which is tidied), and the person's next Keep or Discard finishes it from what git shows: each step of a Keep is skipped when a repeat finds it done, and a Discard of what a Keep brought in already tidies up and is `kept`. A folder under `<data>/worktrees` that no thought records is removed only when it is provably a launch's (its name is that of a launch attempt the store records, which stopped between making the worktree and recording it, so no run began in it), and only as a tidy removes one: on its branch with nothing in it, by `git worktree remove`, its branch from the commit it is at and only when the project folder's HEAD holds that commit too. Anything else there is left alone, and so are pending changes, however long they wait. What a reply would have said is not kept: where the core stops between git's fast-forward and the reply that it went into another branch (the table of Keep), that branch has the commits, the changes are pending, and only git shows why. The files of looks and commands that stopped (`.tmp-*`) are removed.
- **Removed or moved behind the core's back.** A worktree folder deleted by hand leaves what its branch holds as the changes; Keep and Discard work on the branch, and a run that needs the worktree makes it again. A project folder moved or deleted stops nothing: Keep refuses, Discard removes the worktree folder, which is Tasktap's, and leaves the branch to the repository wherever it went.
- **Git as the core runs it.** A command, never a library, found on the terminals' PATH, in the checks' fixed environment, its output written to files of the core's (so one that outlives its core is not ended by writing to nobody), each with a deadline: 60 s for one that reads, 600 s for one that writes a whole tree. A command past its deadline is ended, except the fast-forward in the person's folder, which would be left with files part written: that one goes on by itself, and the Keep replies that git is still updating the folder. Set on every command: hooks off (`core.hooksPath` pointed at a folder that never exists), `core.fsmonitor`, signing, automatic gc and maintenance, recursing into submodules and `core.safecrlf` off; color off and the prefixes `a/` and `b/`, since the core reads the output; and `status.showUntrackedFiles=normal`, so that git's own check before it removes a worktree sees untracked files whatever the person prefers. In the environment: `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0` (a look never takes the project folder's index lock), `GIT_LITERAL_PATHSPECS=1`, `GIT_NO_REPLACE_OBJECTS=1`, `GIT_NO_LAZY_FETCH=1` (in a partial clone a missing object fails the command instead of starting the remote's program; git 2.45 or newer, and an older git does not know it) and `GIT_CEILING_DIRECTORIES` at `<data>/worktrees` (a folder there without its own `.git` is no repository); `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_NOSYSTEM` pass through where the core has them. Diffs are read without external diff programs, text conversion or renames. Everything else is the person's configuration (tier 3): filters and Git LFS, merge drivers, conditional includes, line endings, excludes. Tasktap's commits carry the person's configured identity, or `Tasktap <tasktap@localhost>`. **Decided:** hooks stay off, because one may wait for input, fail or take long in a command nobody watches. Filters and merge drivers run, because without them Tasktap stores or writes a file otherwise than the person's git does, and had to refuse every repository that uses Git LFS. What a configuration can make git run is not enumerated: each list of it was escaped by the next case (conditional includes, lazy fetching, a signature program), and the person's configuration is theirs.

**Answering from outside the terminal: the trial (package D).** A waiting hook can decide a permission request in both tools, and Claude Code's questions; a question Codex asks can only be shown. The evidence, from live runs of Claude Code 2.1.326 and Codex 0.169.0:

- Claude Code, permission request: a `PermissionRequest` hook prints `{"hookSpecificOutput": {"hookEventName": "PermissionRequest", "decision": {"behavior": "allow"}}}`, or `"deny"` with a `message` (a text answer is that message, as Claude Code's "No, and tell Claude what to do differently"). Run with `--permission-mode default`, a Bash command the hook allowed ran and wrote its file; one it denied after 7 s did not, and the model said it was declined. Claude Code shows its own dialog in the terminal while the hook waits and takes whichever answer comes first.
- Claude Code, question: `AskUserQuestion` asks permission as a tool does, and a hook that allows it with `updatedInput` set to its input plus `answers` (the question's text mapped to the chosen option's label, or to free text) answers it: a choice and a free text both reached the model. Through the core in auto mode (`tests/live.rs`): the question opened with `reply_via: core` and the options as choices, a device answered, the hook printed the answer, the receipt was delivered and the run replied with the choice. Answered in the terminal instead, the hook goes on waiting, so the `PostToolUse` of that call reports `continued` naming it: the core settles it as answered in the terminal, and the hook prints nothing.
- Codex, permission request: the same output decides. Codex waits for the hook before it shows its own approval (during an 8 s wait its terminal showed only "Working"), so while a hook waits the person answers from the notch; an allowed command ran, a denied one did not. After 600 s the hook is ended; that Codex then shows its own approval is not verified.
- Codex, question: `request_user_input` exists in plan mode only, or with the feature `default_mode_request_user_input`. Only `PreToolUse` and `PostToolUse` run around it; `PreToolUse` can allow, deny or change the call's input but not give its result. So the question is shown in the notch and answered in the terminal (`reply_via: terminal`), and its `PostToolUse` closes it. Answering it from the notch would need a hook between the question and its answer whose output carries the answers, as Claude Code's permission request does.
- A plugin a person installs can end a waiting hook early. On the trial's computer a Claude Code plugin's "hook guard" ends any `PermissionRequest` hook after 10 s, 250 ms in auto mode, and Claude Code goes on with its own dialog; with it on, only an answer that fast counts from the notch. Its own setting turns it off; Tasktap leaves the person's plugins alone.

**Trust.** A project the person added to Tasktap is a folder they chose to work in, so a run there must not stall unseen on the tool's folder-trust prompt, and Tasktap never writes the tools' own configuration to arrange it. Codex is told for each run that the run's folder is trusted (`-c projects={"<cwd>"={trust_level="trusted"}}`), as 1.2 trusted a folder the person had chosen, so it neither stops at its trust prompt nor writes `~/.codex/config.toml`. The setting adds to the person's `projects` table, it does not replace it: with a `CODEX_HOME` of its own whose config trusted folder B, a run in B given `-c projects={"/elsewhere"={…}}` showed no prompt, while an untrusted control folder did (Codex 0.169.0). The dotted form `-c projects.<path>.trust_level=…` is not used: Codex splits the key on every `.` and honours no quotes, so it fails for any folder whose path has a dot. Codex runs a hook only once it is trusted: the probe trusts exactly Tasktap's, for that run. Codex 0.169 has `--dangerously-bypass-hook-trust`, which would run every untrusted hook, a project's too; it is not used.

Claude Code 2.1.326 has no way to trust a folder for one interactive run. Its record is `projects[<folder>].hasTrustDialogAccepted` in `~/.claude.json`, which `--settings` cannot set; `--trust-workspace` belongs to `claude ultrareview` alone; `-p` skips the dialog only because it is not interactive; and the variables that skip it are internal (`CLAUDE_CODE_SANDBOXED` also claims a sandbox and lifts other checks; `CLAUDE_BG_WORKSPACE_TRUSTED` is for its own background sessions). In a folder it does not trust it shows its dialog before anything else and runs no hook until it is answered (a `SessionStart` hook ran at once in a trusted folder and not at all while the dialog showed), so the session would stay starting with nothing saying why. So the adapter names the dialog's words (`prompts`), the launcher has the core read the run's terminal for them until the agent is ready, with control sequences read as word breaks since Claude Code places each word with a cursor move, and the state machine opens a question answered in the terminal (`shown`, §5): "Claude Code is asking whether to trust this folder". The notch shows it with "Answer in terminal"; `ready` closes it as answered there; "No, exit" ends the run, which withdraws it.

**Starting with no window.** Both tools ask their terminal questions as they start, found by running each under a pseudo-terminal and logging what it wrote. Codex 0.169.0 asks the kitty keyboard flags (`CSI ? u`), the primary device attributes (`CSI c`), the cursor position (`CSI 6 n`) and the default foreground and background colors (`OSC 10 ; ?` and `OSC 11 ; ?`, ended with ST), and waits for them: unanswered, it went on after about 250 ms with its defaults here, not at once. Claude Code 2.1.326 asks its terminal's version (`CSI > 0 q`), the kitty flags, `OSC 7501 ; ?` and the primary device attributes, and does not wait. A page that attaches later mutes the questions it replays, so while no client is attached the core answers them itself (§9): the device attributes, the cursor position and the two colors, the questions a program waits on. It leaves the kitty flags, the version and `OSC 7501` unanswered, as a terminal without them does, so the tools use their plain keyboard: a device attributes answer that comes with no kitty answer before it tells them so. A live Codex run with no client attached went from capture to its result in 5.9 s.

**Where the installed tools differ from inv. §5.1.** Codex runs `SessionStart` with the first prompt, not at start; it allows an `Interrupt` hook 3 s at most; it no longer accepts `-a untrusted` (only `on-request` and `never`); it stops at its trust prompt unless the run's folder is trusted, which 1.2 set only on its older launch path; and the folder must be named as Codex resolves it (`/private/var/…` on macOS, not `/var/…`). `SessionEnd` is not hooked: the core sees an exit itself. Claude Code gives every hook of a turn `prompt_id` and a sub-agent's `agent_id`, has `StopFailure`, and gives `PermissionRequest` no `tool_use_id`; it asks permission for `AskUserQuestion`, which is what lets a hook answer it. 1.2's own `PermissionRequest` hook only reported, and its hooks ran 3 s.

The other four, when they return: **Pi** and **OpenCode** have plugins (`observers/pi.mjs`, `observers/opencode`); each shrinks to a few lines that run `tasktap event`, with no resume, and brings its shim rules with its adapter. **Cursor** and **Antigravity** have no hooks: their thoughts move on launch and exit only, and they can ask through `tasktap ask` if told to in the prompt.

## 8. Routing and speech

```ts
type Key = `p${number}` | `s${number}`                 // a project or a session, by its place in the request
type RouteRequest = { thought: string; current: Key | null; picked: Key | null;
  projects: { id: Key; name: string; aliases: string[] }[];                                                 // ≤ 8
  sessions: { id: Key; name: string | null; task: string; project: Key; agent: string; state: string }[];   // ≤ 8
  recent: { session: Key; request: string; status: string; result: string }[] }                             // ≤ 3
type RouteResult = { quote: string; confidence: "clear" | "ambiguous" | "unknown"; to: Key | "";
  candidates: Key[]; brief: string; title: string }
```

- **One call routes a thought and writes its brief** (plan, "The brief"; built in Phase 3, `core/src/route.rs`). The core builds the request from its own records: the projects and sessions the capture names first, then the session it was made in and that session's project, then the newest; each session with the last request it got (180 characters), and the three latest exchanges with those sessions (the request, 320 characters; how it ended; the first line of the result, 160). Short keys replace both the indexes of 1.2 and the core's ids: a small model copies `p3` without error, and no id leaves the core. The result has only what the core uses. `mode` follows from the destination (a session: a follow-up); who answered, and why not the model, is the thought's `route`, not the model's to say; `difficulty` and `scopeEvidence` chose a model tier in the 1.2 interface and choose nothing here; `agent`, `viewer`, `note` and `question` were never read (hazard 20); `constraints`, which 1.2 used to append to the brief what the brief had lost, is gone with that rule (below). `title` is new: a few words that name the work. Every field is required and none may be added, which is what the strictest of the tools wants of a schema; an empty text or list says "none".
- **The instructions** are the product, and they are one file, `core/src/route/instructions.md`: sent in full before the request with every thought, and shown to the person by `route.terms` before they consent. They make the model decide the destination only from what the person said and the candidates given; quote the words that tie a follow-up to its session; answer `ambiguous` with the candidates rather than guess, also when the thought is work for an agent and nothing points anywhere, and `unknown` only for what is no work for an agent; write a brief that states the goal (the last one, when it shifted), keeps every constraint in the person's wording, resolves references against the sessions and recent exchanges, says what counts as done only if the person did, adds nothing they did not say, is in their language with their terms, and is as short as the thought allows; return a short, clear thought unchanged as its own brief; and give the work a title of two to five words in the person's language.
- **What the core enforces**, whatever the instructions made of the answer (`route::accept`, proven as a table in `tests/route.rs`). An answer that breaks a rule is not used at all:

| Rule | Otherwise |
| --- | --- |
| at most 64 KiB, and the one JSON object of the schema with no other field | rejected |
| a destination, and every choice, is a key the request offered | rejected |
| a follow-up to a session quotes at least 3 characters found word for word in the capture (case, punctuation and spacing aside); one to the session the capture was made in needs no quote, as the local router sends it there without words too | rejected |
| `ambiguous` names at least two different choices | rejected |
| a brief is there (except for `unknown`) and is no longer than twice the capture plus 400 characters | rejected |
| a title is one line of at most 60 characters, with no control character | the thought has no title; the rest of the answer is taken |
| the person picked the destination | only the brief and the title are taken; where the model would have sent it counts for nothing |
| the destination went while the model was asked | the thought stays an idea, its `route` saying so |

  The rule of 1.2 that appended to the brief a constraint found word for word in the capture and missing from the brief is **dropped**, and with it the `constraints` field. It existed because 1.2 sent the agent the brief alone. Here the person's words travel with every brief, so the appended line only repeated them: in the evaluation every brief already had every constraint, and each append was a duplicate of a sentence worded slightly differently. Without the field every constraint was still in every brief of both tools (below), and the answers are shorter and half a second to a second faster.

- **When a model is asked, and what happens when it gives nothing** (rows of §5; `effects.rs` carries them out):

| The capture | Who routes | Brief |
| --- | --- | --- |
| no consent (`route_by` unset, or naming another model than this core would ask) | the local router | the person's words |
| at most 160 characters on one line, and the local router is sure where it goes | the local router: nothing is sent anywhere | the person's words |
| anything else without a destination | the model, within its time limit (12 s for Claude Code, 15 s for Codex); the thought is `captured` and its `route` pending meanwhile | the model's |
| a destination the person picked, the thought at most 160 characters on one line | nobody | the person's words |
| a destination the person picked, a longer thought | the person; the model is asked for the brief alone, the thought `routed` and its `route` pending meanwhile | the model's |
| the model fails, takes too long, or its answer is rejected | the local router, or the person's pick; `route.fallback` says why, in words (`claude: it did not answer within 12 s`) | the person's words |
| longer than 8000 characters | the local router; `route.fallback` says so | the person's words |

- **The person's words travel with the brief.** A run is told the brief and then, marked as theirs, what the person said, so the agent can check one against the other; each adapter says how (`Agent::told`). Claude Code: the brief, a blank line, `The text above is a brief written from what the person said. What they said follows, word for word; where the two differ, their words count.`, and the words in a `<persons_words>` tag. Codex: the brief, a rule (`---`), the same sentence, a blank line, the words. A follow-up is typed the same way. When the brief says the same words as the capture (case, punctuation and spacing aside), the capture alone is sent, once.
- **Timing and the hold.** The router is asked at capture and works during the hold, which counts from the capture: a route that arrives after 2 s leaves 3 s of a 5 s hold. What arrives late is still read: the hold ends no earlier than 2 s after the route, or the brief of a picked thought, arrived (§5, `READ_HOLD`), so a brief is always on screen for a moment before the launch, and a thought that needed no model keeps the plain hold. The brief is written into the thought the moment it arrives. Undo, during the hold or while the router is still asked, ends the tool's process; `thought.start` waits for nothing. `route.hint` stays the local match: no model call per keystroke. Measured on an Apple M4 Pro, 2026-11-17, each call a new process with nothing kept warm (the second call of a pair was no faster than the first: 2.25 s after 2.28 s for Claude Code, 4.4 s after 4.2 s for Codex), on the instructions as committed:

| Tool, model | A one-line question | A spoken thought, routed and briefed (median; range) | Of 14 thoughts, later than a 5 s hold |
| --- | --- | --- | --- |
| Claude Code 2.1, `haiku` | 2.1 to 2.3 s, of which about 1 s is the program starting | 3.7 s; 2.0 to 6.6 s | 3 |
| Codex 0.169, `gpt-6-luna`, low reasoning | 3.7 to 4.4 s (6.6 s with its tools left on) | 4.7 s; 3.6 to 5.9 s | 3 |

  So a spoken thought usually starts when its 5 s hold ends, and about one in five starts up to 2 s after its route arrived instead, 8.6 s after the capture at the latest seen. Claude Code's model thinks before it answers (about 500 of its output tokens), and no flag or setting of the tool turns that off; Codex takes about 4 s for a one-line question already. The web provider below can ask the same model without the program's start (about 1 s) and with its thinking off. No process is kept warm.
- **Consent.** Routing by a model sends the thought, the names and aliases of up to 8 projects, of up to 8 sessions their name, last request, agent and state, and of up to 3 recent exchanges the request, how it ended and the first line of the result, to the provider behind the person's own installed agent, under the sign-in that agent already has. It happens only with the person's consent, which is one preference: `route_by {agent, model}`, the tool and the model the consent covers. Putting it is consenting; `route.terms` gives the interface what the person must have seen first (the instructions in full, what is sent, and for each agent that can be asked the model it asks). The core refuses a `route_by` that names an agent it does not have or another model than it would ask (`invalid`), and ignores a stored one that no longer matches after an update: the consent then covers something else, the local router routes, and `route.fallback` says so. A tool that answers that it no longer offers the model (each adapter reads that from what its tool printed: `Headless::gone`) is not asked again while the core runs and is left out of `route.terms`; every thought is then routed by name at once, and its `route.fallback` says, in words the interface shows as they are, `Codex no longer offers the model Tasktap asks for routing; routing by name until Tasktap is updated`. Changing the tool is putting the preference again, after the same screen; deleting it ends model routing. **This replaces `connections.consent` for the command provider:** a connection record was designed for providers the core signs in to itself (a server, a key, an account), and the person's own agent needs none of that. There is no separate choice of router: the tool named in the consent routes. The interface offers the default agent first.
- Three kinds of provider behind one function. **Command** (`claude -p`, `codex exec`) is built: the tool is spawned off the core's thread in `<data>/route`, a folder that holds nothing but the schema, with the fixed environment of an agent's checks, the question on its standard input, no tools, no session saved, none of the person's or the project's instructions, and the smallest fast model the tool offers; each adapter says how (`Agent::headless`, §7). Its answer is taken the moment it is whole on its standard output, and the process is ended then: Claude Code was seen to stay on for 8 minutes after it had printed its answer. **Web** (OpenAI, ChatGPT sign-in, Anthropic, a model server), called by the core, and **host** (the on-device model) through `host.model` are not built; their seam is `effects::route`, which asks one function for a JSON answer to `route::question` and hands it to `route::accept`. A local match on names and aliases answers `route.hint` and is the fallback.

- **The local router (built in Phase 2, `core/src/route.rs`).** A pure function over the request the core builds from its records: the open projects whose folder is there, with their names and aliases, and the sessions a follow-up can reach in them (not ended, or ended with a resume handle). ### Speech

A dictation becomes a thought exactly as typing it would have been, or only words for the person to send themselves (plan, "Speech"; built in Phase 3: `core/src/speech.rs`, its rules in `state.rs`). Whoever records, a host or a page, calls `dictation.start` and is the dictation's **recorder**. Local engines stay with the recorder; a speech service is called by the core, so it works the same on every system. Nothing is started from audio that typing could not have started, and nothing but a new thought, which has its hold and Undo, is sent from audio at all.

```ts
type Dictation = { id: Id; rev: number; phase: "recording" | "transcribing" | "heard" | "failed"; text: string; level: number;   // 0 to 100
  target: ({ kind: "thought" } & Capture) | { kind: "text" }; error: string | null }
// dictation.start {id, target, local} → {stream: Opened | null, seconds: 300}
// dictation.report {id, text?, level?}    dictation.finish {id, as?: "text"}    dictation.cancel {id}
```

- **The record.** `dictations` is a collection in memory only: one row for each dictation that is under way, or that ended without becoming a thought. One records at a time; up to four are under way, so the person can speak the next thought while the last is still being transcribed. A dictation that became its thought leaves no row: the thought is what it became. One that was only to be heard stays as `heard`, its words in `text`, and one that failed stays as `failed`, with why in `error` and whatever was heard in `text`; either until `dictation.cancel` dismisses it or the next `dictation.start` clears it.
- **The target** is one of two. `thought` is a new thought, spoken from the notch or into an empty Composer: a capture as `thought.capture` takes it, so it carries the id of the thought to be, the destination the person picked if any (`project_id`, or `session_id` for a follow-up to a session), `current`, the agent and the model; its `source` must be `voice` and its `text` empty, since the transcript is its text. It is captured and routed as any capture is, so the hold, routing, the brief and Undo all apply. `text` is speech into a field: the answer to a question, or a thought the person has half typed. The dictation then ends as `heard` with the words in its row, the core captures nothing and sends nothing, and the page that has the field places them at its caret and dismisses the row; the person reads them and sends with Return, so what is sent is what they saw. **There is no target that answers a question**, decided by the owner on 2026-11-18: a word heard wrong could approve or redirect an agent with nothing to stop it, where a thought heard wrong sits in its hold. For the same reason of one mechanism there is no "typed text before the transcript" in a `thought` target: a field that holds text is the `text` target's. The words reach the page, and a recorder that wants them, as the row; `dictation.finish` answers at once and returns nothing. **A spoken thought as words only**: the person speaks into the empty Composer, lets go, and wants to read or edit before sending. That is known only when they let go, and starting every such dictation with the `text` target would give up what the `thought` target is for (the thought is captured by the core, whether or not the page that started it is still there), so the finish says it: `dictation.finish {id, as: "text"}` turns the dictation's target into `text`, and from there on it is that target's one path, nothing new. It counts until the thought is captured, so also in a second finish while the words are on their way; after that there is no dictation (`gone`), and the thought is in its hold, where Undo is.
- **The audio** is raw PCM, 16 kHz, one channel, signed 16-bit little-endian, on the stream `dictation.start` opened: 32 000 bytes a second. Raw, not compressed, because nothing has to be built for it twice: every recording interface on both systems gives samples, and a compressed format is one encoder per system (the webview's recorder gives WebM with Opus in WebView2 and MP4 with AAC in WKWebView) or a codec in the host. Both providers take WAV, which is these bytes behind a header of 44; Groq's documentation says its models resample to 16 kHz mono anyway and recommends WAV for the lowest latency. A spoken thought of 20 s is 0.64 MB. **Bounds:** 300 s, which is 9 600 000 bytes: the core grants credit for that many and no more, so a recorder cannot send more, and they are held in memory until `dictation.finish` (the buffer grows by doubling up to that many bytes and no further) and then handed to the thread that writes them, whole samples only, to one file for the upload, so the core's thread never holds them again. A byte sent beyond the credit ends the connection, as on every stream, and with it the recording. That is under the 25 MB both providers take. A recording that has not ended 10 s after its 300 s fails.
- **The level** is derived by whoever has the audio. With a stream the core takes the peak of each 100 ms of samples as they arrive (0 at −55 dBFS, 100 at −6 dBFS, the scale of 1.2) and publishes the row when it changed: the recorder does nothing for it, and the core needs the samples' peak anyway, to know a recording in which nothing was heard. A recorder that transcribes itself has no stream and reports `level` with its partial transcript through `dictation.report`. No timer either way: the audio is the clock.

| Event | Dictation |
| --- | --- |
| `dictation.start` | → recording, its deadline 310 s on. With a speech service consented to (below) the reply carries the stream and the core transcribes; without one `stream` is null and the recorder transcribes. Rows that ended, `heard` or `failed`, are removed. `conflict` while another records, while four are under way, or for an id in use; `failed`, "No speech service is set up", when there is no consent and the recorder cannot transcribe (`local: false`); `invalid` or `conflict` for a target typing could not have had: a capture whose source is not `voice`, whose text is not empty, whose agent or model `thought.capture` would refuse or whose thought exists already. A destination that goes while the person speaks is refused at the capture, with the words kept |
| audio on the stream | kept, up to the bound; `level` follows it |
| `dictation.report` while recording | the recorder transcribes: `text` (the transcript so far, whole) and `level` replace the row's. `conflict` for a dictation the core transcribes |
| `dictation.finish`, from the recorder's connection after its last audio (`denied` from another: only frames on one connection arrive in order) | recording → transcribing. With `as: "text"` its target becomes `text` first, while it records or is transcribed: what was started for a thought is then only heard, and nothing is captured. The core transcribes: when nothing was said (below) → failed, "Nothing was heard", and nothing is sent; otherwise the web call starts, with its own time limit. The recorder transcribes: its transcript is waited for, for 120 s |
| the transcript arrives: the web call's answer, or `dictation.report {text}` while transcribing | empty → failed, "Nothing was heard". Otherwise, for a `thought`: captured at once with `source: voice`, and the row is removed; refused (the project went, the session ended): failed, the transcript in `text` and the refusal in `error`, so the words are not lost. - **Nothing was said** when the recording is under 0.1 s; when none of it is above −55 dBFS, as a microphone that is muted or refused gives zeros; or when it is as even as an empty room: at least half a second long, with no tenth of a second twice as strong (3 dB) as its weakest tenth, and none at −30 dBFS or above. The last costs two sums a sample and keeps three numbers; it has no state of its own and nothing to tune per microphone, since the recording is its own measure. It errs on the side of sending: a click, a gap in the noise, a room whose noise wanders by 2 dB or more, a recording too short to tell, and any loud place are all sent, as before. What it refuses besides a room is a steady sound quieter than −30 dBFS, and speech that never rises above the room's own noise. **How that was tried** (2026-11-18, no microphone: "Ja", "Nein", "Okay" and "Stopp" from the Mac's German voice, mixed into even noise at −50 and −40 dBFS, with and without a pause around the word): every word at or above the level of the noise was sent, and every one 3 dB below it was not; an empty room was caught at every level from −60 to −35 dBFS and with its noise wandering by 1 dB, and no longer with 2 dB. A stricter rule, two tenths in a row, which would also ignore a click, refused "Stopp" at 10 dB above the noise and was dropped. **Not known:** how often a real room is that even. A microphone whose gain the system raises during silence, or keys and breath near it, will pass as said, which costs one call and, from a model that invents words for silence, a thought that sits in its hold. No real microphone was used for any of this.

## 10. Efficiency

One thread owns all state and runs a single-threaded `tokio` runtime, so there are no locks. Blocking work (terminal reads and writes, waiting for exit, web calls, git, the folder checks of `project.add` and `project.scan`, four at most at once, a launch's search for its program and its probe, and the writing of a terminal's history, since a stalled network mount blocks them for as long as the system lets it) sits on plain threads that sleep in the kernel and send a message when something happens.

| Dependency | Why it earns its place | Phase |
| --- | --- | --- |
| `tokio` (current-thread; `net`, `io-util`, `time`, `process`, `signal`, `sync`) | Sockets, named pipes, peer credentials, one-shot timers, child processes with time limits and signals on three systems from one crate | 1 |
| `rusqlite` (bundled SQLite) | The store; calls are synchronous on the core thread | 1 |
| `serde`, `serde_json` | The protocol | 1 |
| `uuid` (v7) | Time-ordered ids clients can mint | 1 |
| `sha2` | Key, token and argument hashes | 1 |
| `ts-rs` (build only) | TypeScript types generated from the Rust protocol types | 1 |
| `portable-pty` | Terminals | 2 |
| `windows-sys`, one more feature (`Win32_Security_Credentials`) | Keys in the Windows Credential Manager; the crate was there already | 3 |

Planned for Phase 3 and not taken (§8, with the numbers): `ureq` with rustls for web calls, which alone is 1.45 MB and puts the binary over its limit, and `keyring`, whose entries make macOS ask for the login password after every update of an ad-hoc signed app. The system's `curl` and the systems' own credential tools do both with no package and no byte.

Not used: an argument parser, error or logging crates, an asynchronous HTTP stack, a file watcher, a git library, an MCP library, a terminal emulator.

**Zero idle wakeups.** The core thread waits in the kernel for one of: bytes on a connection, a chunk or an exit from a terminal thread, a signal, or a timer that something armed. Every timer fires once: the hold before launch, the 2 s kill, the 1 s a terminal waits for its output to end after its child exited, the 60 s exit, a new connection's 5 s to say `hello`, a time limit on a web call or spawned command, a dictation's deadline. Nothing repeats. Projects are scanned when a client asks, not watched. SQLite checkpoints on the write path.

| Measure | Target | 1.2 |
| --- | --- | --- |

**With routing by a model (Phase 3):** every row still passes on the same machine; idle 0 wakeups, memory with no terminals 3.1 MB, start 4.1 ms. **The single pass-through.** The host gives each page one object and nothing else:

```ts
interface Bridge { send(frame: string | Uint8Array): void; host(frame: string): void; onframe: (frame: string | Uint8Array) => void }
```

`send` and `onframe` are an untouched pipe to that page's core connection; the host does not parse core-bound frames. `host` carries the `host.*` calls, which the host answers itself, so a window drag never waits for the core. The shared client decides by the call's name; pages never ask which platform they are on. The host is also a client of its own: it declares its abilities, publishes the `host` record, and answers `host.*` calls from the core.

## 13. Layout and tests

```

core/src/main.rs         picks the role from the program name or first argument

core/src/state.rs        the state machine and attempts;   questions.rs: ask, answer, withdraw, received
core/src/terminal.rs, agents.rs (trait, registry), agents/ (claude.rs, codex.rs, rules.rs, checks.rs)  (Phase 2)
core/src/roles.rs        event, hook, ask; roles/shim.rs, roles/fixture.rs; shim.rs: adopted agents (2)

core/src/http.rs, secrets.rs, command.rs   a web call through the system's curl; keys in the system's credential store; a program run within bounds (3)
core/tests/              one file per promise, plus fixtures/
```

**Tests** start the real binary on a temporary data folder and speak the protocol through `client.rs`. No test reaches into the core. Fixtures are part of the binary under a test-only feature: `fixture.stream` (a call that opens a stream of known bytes and echoes what it receives, so streams, credit and bounds are tested before terminals exist), a fixture launcher and route provider, and from Phase 2 `tasktap fixture-agent`, which prints, sends events, asks, waits and exits in a real terminal on every platform without shell scripts. `fixture.script {agent}` has the real launcher start that agent, found on the core's PATH as `fixture-agent`; without it the fixture launcher stands in, kept only where a test scripts what the real one cannot do (a launch the store refuses, an answer never confirmed).

**The one check at the end of every phase:** `cargo test -p tasktap-core --test loop`. Capture a thought; route it (the fixture provider answers `clear`); run it; the agent asks; answer it; the agent finishes. It asserts the status sequence captured, routed, working, needs you, working, done; a result tied to the thought; an answer receipt marked delivered; then restarts the core and asserts that every record is still there and that nothing ran again. In Phase 1 a test client holding a session token stands in for the agent; from Phase 2 the fixture agent runs in a real terminal the real launcher started, its steps typed into it and its reports sent through `tasktap hook`, and the assertions do not change. Its restarts end the core as a crash does.

## Defaults chosen

Each is the default so that building is not blocked. The owner may overrule any of them.

1. **Voice waits for Enter, except for a new thought.** A new thought spoken from the notch is captured when the dictation ends and is routed and held as a typed one is: the hold, with the brief on screen and Undo, is what stands between a mishearing and work. Everything else that is spoken, an answer to a question and text dictated into any field, is only shown where it was spoken into, and the person sends it with Return (§8, the `text` target): the core never answers a question from audio. Decided by the owner on 2026-11-18, after a first build that sent a spoken answer at once.
2. **Undo is a hold. Changes the plan.** A clear thought shows "Sent to X" at once and launches when the Undo seconds have passed. The duration is a preference; zero launches at once. Stopping an agent after it started could not take back what it did in a project that is not isolated.
3. **A prompt typed by hand becomes a thought**, so Home and the glance list everything in flight.
4. **Nothing comes over from 1.2** (the owner's decision, §11): the new app starts empty, and a session still running in 1.2 is not carried over.
5. **Dropped:** Resume in Terminal and copy-resume (never worked), the Claude brief session in Terminal.app, the discussion step before an answer (a text reply), the terminal typing trace, questions from tools outside Tasktap's terminals. Agent sign-in moves from Terminal.app into a Tasktap terminal that belongs to no project (Phase 2).

Still open: **one host or two**, which trial T settles.
